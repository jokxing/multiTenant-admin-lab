# MultiTenant Admin Lab

面向前端岗位的后台工程作品，从实际 SaaS 后台工作中提炼配置驱动页面、公共组件、权限协作及移动端编排经验。当前使用模拟业务数据展示，不提供生产业务后端。

基于 Vue 3、TypeScript、Vite、Naive UI、Pinia 和 SoybeanAdmin 构建。

重点案例是配置生成列表中的复杂排序和多语言素材组表单：展示如何把通用结构交给配置，把复杂交互封装为组件，并通过统一动作入口处理保存、失败反馈及状态恢复。

## 核心能力

### 页面配置与发布

- JSON Schema 与可视化设计双向同步
- 动态表格列、表单字段和操作按钮配置
- `form`、`confirm`、`slot` 三类操作执行器
- 操作表单、条件显隐、校验规则和动态预览
- 草稿差异、发布校验、版本记录与回滚
- 搜索、筛选、虚拟滚动和个人列偏好
- 配置驱动列表排序（内容推荐列表：拖拽 / 置顶 / 上移 / 下移）
- 配置驱动复杂表单（多语言素材组：简/繁/英 + 本地素材样例）

### 角色权限演示

- 平台超管、租户管理员、审核专员三类角色
- 页面 Schema 自动注册按钮权限点
- 权限树编译为 `route_keys`
- 页面级与按钮级权限过滤
- 待发布变更、策略发布和内存审计记录
- 配置视图与角色视图对照验证

### 实时待办与消息处理演示

- 连接状态恢复模拟与退避延迟公式
- 消息唯一 ID 和当前页面内去重
- 突发消息顺序消费队列
- 多业务待办计数聚合
- 分类声音偏好和音频串行队列
- 事件流水与消费指标

## 推荐演示路径

1. 在“页面配置器”新增表格列或操作按钮。
2. 为 `form` 类型按钮设计操作表单。
3. 查看草稿差异并发布新版本。
4. 切换角色视图，观察未授权按钮被隐藏。
5. 前往“角色权限配置”发布按钮权限。
6. 返回角色视图或权限实验台验证结果。
7. 在实时消息中心演示重复消息和断线重连。
8. 新建或打开“内容推荐列表”，发布后在运行时演示排序列（含保存失败回滚）。
9. 新建或打开“多语言素材组表单”，发布后演示语言切换保留输入、校验定位与保存失败保留。

类型检查、生产构建与业务验证：

```bash
pnpm typecheck
pnpm build
pnpm test:demo
```

## 设计与面试讨论

详细背景和源码按主题整理：[配置与运行时](docs/project-guide.md#配置到运行时)、[复杂排序](docs/project-guide.md#代表案例一配置生成列表的复杂排序)、[多语言表单](docs/project-guide.md#代表案例二配置与复杂表单组件组合)、[权限](docs/project-guide.md#配置与权限联动)、[消息处理](docs/project-guide.md#消息去重与消费队列)、[双端协作](docs/admin-mobile-integration.md)。以下回答针对当前作品，历史职责单独注明。

### 基于 SoybeanAdmin，个人贡献体现在哪里？

框架提供布局、主题、路由基础与通用组件。本人在原项目中主导 SaaS 后台前端，负责技术选型、结构、需求拆解、接口协商、复杂功能、公共组件及代码评审。当前作品通过配置驱动列表、排序、复杂表单、权限协作和编排案例展示这些经验，提炼过程使用 AI 辅助；配置发布与回滚是本次新增能力。

### 为什么采用配置驱动，又保留专用业务组件？

后台很多列表和表单的结构相似，列、搜索项、字段及按钮适合由配置表达。多语言输入、素材选择和校验定位等交互交给专用组件，再以 `lang-asset-group` 接入配置。配置负责结构和组合，组件负责具体交互；当前提炼这一思想，不完整复现原后台配置引擎。

### 拖拽、置顶、上移和下移为什么走同一个入口？

四种操作改变的是同一份列表顺序，统一走 `dispatchSortAction`，共用身份查找、提交锁、保存与失败回滚。使用稳定实体 ID 标识内容，显示索引只表示当前位置，移动后不会把另一条数据误当作原记录。

### 为什么有筛选条件就禁用排序？

筛选结果只展示完整列表的一部分，当前作品没有定义隐藏项与可见项之间如何排序。允许直接调整会产生顺序歧义，所以先清空筛选再调整完整列表。跨页或筛选范围内排序需要先约定业务范围与接口语义，当前示例不覆盖。

### 排序保存失败、连续点击时怎样保持一致？

操作前保留原顺序，先更新界面再进行异步 Mock 保存；失败恢复原顺序并提示重试。提交期间禁用控件，动作入口也检查提交锁，避免多个请求互相覆盖。当前锁属于单个交互实例；真实服务的多用户并发、超时后是否落库，还需要服务端版本校验和状态查询等机制。

### TypeScript 已检查类型，为什么还要校验 JSON？

TypeScript 约束代码中的类型，用户输入的 JSON 仍是运行时未知数据。应用前检查字段名、组件类型、语言配置及正则，发布前再检查相关配置。非法表单 JSON 在写入前拒绝，保留原有效配置和未保存输入；当前校验不是完整通用 JSON Schema 标准验证器。

### 多语言校验为什么不能只显示一个“表单有误”？

错误按“字段 + 语言 + 子字段”定位，各素材组只接收自己的错误，并切换到出错语言。主语言标题必填，其他启用语言为空时可选，填写内容后再检查标题等规则。配置必须包含主语言，避免必填项被隐藏后无法修正。

### 多个素材组、切换页面和异步保存怎样避免串数据？

草稿按页面与字段隔离，同一页多个素材组一次保存。提交时克隆快照，失败保留当前输入；结果返回时核对页面标识，避免把旧页面的结果回填到新页面。组件用克隆值和事件更新模型，不直接改写外部共享对象。当前保存范围是素材组数据，不代表整张业务表单已接入后端。

### 隐藏按钮就完成权限控制了吗？

前端权限负责菜单、页面及按钮的展示体验。原项目由后端根据角色和菜单规则提供权限，本人负责前端协作与展示；当前作品用本地角色模型模拟这一过程。真实接口仍需校验身份、操作权限和租户归属，不能依靠浏览器隐藏按钮保护数据。

### 消息去重、业务队列和声音队列分别解决什么？

按消息 ID 去重，避免同一事件重复进入消费；业务队列顺序更新计数，声音队列串行播放提示音。内容相同的两条消息可能是不同事件，不能只按文字去重。当前页面以本地事件演示，去重集合不跨刷新，也没有真实 WebSocket、消息补偿或生产可靠性保证。

### 为什么回滚会产生新版本，而不是删除后面的版本？

回滚也是一次发布操作，新记录可以表达“何时恢复了哪个快照”，保留此前版本和操作顺序。当前记录保存在 localStorage，用于演示草稿与发布状态；多人发布冲突、审批和持久化审计需要服务端支持。这项能力属于展示阶段新增。

### 后台编排和移动端是什么关系，发布后是否已经上线？

两个工程独立运行，后台编辑首页和活动配置，移动端通过 iframe 预览协议接收并渲染。双方校验消息来源和配置，后台发布记录保存在自身浏览器，预览不等于上线部署或共用数据库。原移动端由另一名前端主要负责，本人负责相关后台配置与跨端协作，详见[双端说明](docs/admin-mobile-integration.md)。

### 类型检查与构建通过，为什么还需要浏览器验证？

这些检查不能覆盖 DOM 挂载时机和实际布局。本次提炼中，拖拽在表格未挂载时初始化，异常影响页面更新，导致弹窗关闭和 JSON 编辑区切换失效；改为 DOM 就绪后绑定，并通过实际浏览器交互验证。素材“已选”提示也需检查选中后的布局。这些是本次展示阶段的复盘修复，验证范围见[记录](docs/implementation-review.md)。

## 原项目与当前作品

本人从原项目开始主导 SaaS 后台前端，负责技术选型、前端结构、需求拆解、接口协商、复杂功能及公共组件封装，并负责后台代码评审。另一名前端主要负责移动端；后来新增前端承担较简单的后台页面配置、菜单及接口工作。

原后台已有配置驱动列表与表单、复杂组件、后端菜单权限和 WebSocket。当前作品提炼这些工程思想，不完整复现原配置引擎；配置发布与版本回滚属于本次 AI 辅助提炼新增能力。框架基础、原项目经历和展示阶段新增实现分别说明，详见[个人贡献与能力来源](docs/project-guide.md#项目背景与个人贡献)。

## 数据与实现边界

- 所有租户、用户、金额和申请数据均为模拟数据。
- 推荐演示账号可本地登录；请求层仍保留上游公共 Mock 服务配置及非演示登录、Token 刷新等请求分支，不能将整个工程描述为完全离线应用。
- 配置版本、排序、素材组草稿和部分偏好保存在浏览器；权限策略与演示审计使用内存状态，没有服务端持久化审计或租户数据隔离。
- 前端过滤按钮不等于接口授权；配置器的预览角色与登录身份分别控制。
- 实时待办页不连接真实 WebSocket；移动端客服 HTTP/SSE Mock 属于另一条链路。
- 列表排序展示完整列表内的调整，不支持跨页与子列表排序；素材为本地 SVG 样例，不提供上传服务。
- 首页提供“重置 Demo”，可恢复初始演示状态。

2026-10-09 已通过示例测试、类型检查、生产构建及两条代表链路的本地 Edge 浏览器回归。完整范围见[验证记录](docs/implementation-review.md#验证命令及结果)，不代表全部模块、设备和浏览器均已验收。
